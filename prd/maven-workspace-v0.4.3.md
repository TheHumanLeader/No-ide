# Maven 工作区源码一致性修复

日期：2026-09-21。状态：实现与回归夹具已提交，等待本次构建实际验证；不预先宣称通过。

## 问题

旧版 spring-maven 只对入口模块执行 compile / spring-boot:run。同工程依赖可能从 Maven 本地仓库拿到旧 JAR；已删除的类或资源也可能留在旧 target 目录。入口模块目录被直接用作应用工作目录，又会改变相对配置路径。不能通过升级框架版本或隐藏错误解决这些问题。

## 实现

只解析可信项目边界内的 POM 声明，有界查找真实聚合根；父 POM 不等于聚合 POM。多模块启动先对入口执行 -pl / --also-make clean install，再对入口单独执行 spring-boot:run。构建与运行沿用相同 Maven、settings.xml、本地仓库及 Maven Profile。install 为本机操作，不执行 deploy，不向 Git/SVN 提交。

首次启动和手动重新构建清理选中构建范围的 Maven 产物。普通文件修改走增量，删除/重命名触发清理。已启用监听时扩展到声明模块的 src 与 POM；不扫描所有源文件来建立 IDE 索引。Maven 决定实际依赖构建图。Maven 构建串行，避免 No-ide 自身并行覆盖共享输出。

模块目录与应用工作目录独立；多模块默认聚合根，用户可通过选择器覆盖。Maven Profile 与 Spring Profile 分开，不自动切换用户 Profile、JDK 或框架版本。提供构建范围预览和可选的类加载来源诊断。类诊断日志有界，不能保证在高流量中无限保留。

## 验证目标

在一次性 Maven 仓库安装同版本旧依赖，再删除类/资源并修改依赖源码。通过旧单模块方式复现旧 HTTP 内容与旧 WebSocket 指令处理；再通过新启动方式验证 HTTP、真实 WebSocket、类缺失检查、资源缺失检查、运行目录与 JAR 字节改变。无关模块放入故意无法编译的源码，验证未无差别构建全工程。再次改同版本源码、热改依赖模块、显式工作目录等都检查真实进程。

夹具只包含合成代码，不上传用户日志、业务代码、私服或数据库信息。用户工程的某个类究竟来自哪个 JAR，仍需要该工程的实际类加载来源，不能由夹具结果直接推断。

## 边界

执行用户的 Maven 生命周期可能运行 POM 已声明的插件。不会自动删除用户数据库或清空整个 Maven 仓库。clean/install 使用原项目构建输出，尚非隔离构建或原子发布；旧进程虽不会被提前结束，但 DevTools/懒加载可能观察到输出变化，不能承诺旧版本运行现场完全不受影响。停止后启动为本次修复最明确的验证路径。

复杂 Profile、外部模块、不同版本同名依赖、定制构建目录与跨工程输出需要额外验证；无权限边界外的模块不会静默访问。高级原始命令不自动改写。修改的是 No-ide 的启动逻辑，不添加用户业务 WebSocket 处理器，也不假造 appender 消失。
